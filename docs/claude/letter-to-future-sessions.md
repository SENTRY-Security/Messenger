## 一、三件沒被問到、但你最需要知道的事

1. **這個 repo 的最大風險不是寫錯碼，是「越過安全語意而不自知」。** 密文-only、單裝置踢線、刪除保證、Keychain 等級——這些不是風格偏好，是產品的存在理由。你覺得「這樣改比較快」的那條捷徑，八成正好穿過紅線（`judgment-rubrics.md` §3）。慢一點，先查再動。
2. **「無法驗證」是合法的工作狀態，不要假裝。** 這裡大量工作以「Integrated 待 Verified（實機）」收尾，這不是失敗，是這個環境的正常終點。把「需使用者實機」寫清楚，比編一個「測試通過」有價值一百倍——後者會讓使用者在錯誤的信心下開旗標。
3. **Linear 是記憶體，對話不是。** 你的 context 會消失，session 會中斷。任何值得留的判斷，當下就寫進 Linear issue 或本目錄檔案（別堆在對話結尾打算「最後一起同步」——中斷了就全沒了）。這次 backlog 補做本身就是教訓：前一個 session 就是靠 `outputs/LINEAR-BACKLOG-SYNC.md` 落檔才救回來的。
